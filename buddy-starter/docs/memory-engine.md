# Memory engine

Memory is off by default and only becomes available after a user opts in. Disabling it stops retrieval; the user can separately delete all saved memories. Sensitive manual memories require an additional explicit consent checkbox and are excluded from chat retrieval. Memories expire when their selected retention time passes. Manual CRUD and basic PostgreSQL retrieval are implemented with per-user filters and active/expiry checks.

Extraction runs after successful account chat commits and is retryable. Each eligible persisted user message is processed under a per-user PostgreSQL advisory transaction lock. A valid structured response, its memory writes, and a `memory_events` completion marker commit together; provider, output-validation, or database failures leave the message pending. Before account-chat retrieval, Buddy retries the oldest pending message, so a service restart or temporary Gemini outage can recover on a later signed-in chat. It also tries one pending message after each successful reply. Messages from before the latest active opt-in are never backfilled. Completion metadata stores message IDs and outcome counts, not chat text.

Gemini returns structured Pydantic-validated candidates with exact evidence quotes from the user's own words, category, sensitivity, confidence and optional event date. Explicit corrections identify the existing fact to replace; automatic corrections update that row instead of creating a competing fact. Candidates without evidence, below the confidence threshold, duplicates, unsupported contradictions, expired events, sensitive details, or facts blocked by a deletion tombstone are not automatically stored. Sensitive candidates remain suggestions requiring explicit user approval. Automatic storage is capped per user. Automatic memories are labeled as learned from chat in the Memories page. Deletion and expiration events keep a SHA-256 fingerprint rather than deleted memory text, preventing retries from restoring a removed fact. Event/open-thread memories may trigger a follow-up only on a greeting, only after their due date, and at most once per user per week; sensitive facts are excluded and the memory is marked as followed up.

Retrieval first filters saved memories by verified user, active status, non-sensitive consent, and expiry. With `PGVECTOR_ENABLED=true` and the extension plus `memory_embeddings` table confirmed present, 768-dimension `gemini-embedding-001` vectors use pgvector cosine distance and metadata overlap/recency scoring. Otherwise saved facts use lexical overlap and bounded topic aliases, then at most five facts are selected.

For signed-in chat only, the same memory opt-in enables a separate PostgreSQL full-text search over user-authored messages in older conversations. Query terms include the current user exchange and topic aliases (so a broad work question can find a project described with different wording). `ts_rank_cd` ranks relevance and message time breaks ties. Search is owner-scoped, excludes the active conversation, and returns at most three excerpts of 600 characters. Matching saved facts are deduplicated. Quick Chat never enters this path. Current messages, saved facts, and past-chat excerpts are sent to Gemini as separately labeled untrusted sources; transcript history remains unchanged in the UI.

Sensitive details are excluded from transcript fallback by suppressing source conversations of explicitly sensitive saved facts and by a conservative sensitive-topic filter. Deleted, expired, and superseded memories produce hash-only tombstones; when source provenance exists, their source conversation is excluded, and candidate excerpts are checked for tombstoned phrases. This provides deterministic protection for exact recalled facts without storing deleted memory text. It does not classify every possible indirect sensitive disclosure; the filter errs toward excluding broad health, identity, financial, legal, location, sexuality, religion, and political terms. Full-text retrieval requires no migration and works with pgvector disabled. The optional vector migration remains revision `0004_pgvector`; the normal local schema ends at `0003_memory_metadata`.

## Learning from chat, check-ins and diagnosis (addendum)

**Why automatic saving was empty.** On the development machine every user had memory enabled with an active consent and 7 to 26 persisted user messages each, but zero `extraction_completed` markers. Every extraction attempt failed at the provider step (`httpx.ConnectError`, the same network failure that blocks Gemini chat), and a provider failure deliberately leaves the message pending. The rest of the pipeline (persisted message, consent recheck, provider call, Pydantic validation, evidence/confidence/tombstone checks, memory write plus completion marker in one transaction) is covered by mocked end-to-end tests; nothing could be saved because Gemini was never reachable. The chat now tells the user "Buddy could not finish learning a detail yet. It will retry during a later chat." instead of staying silent, and `memory_extraction {...}` log lines carry outcome counts (`provider_failure`, `invalid_output`, `saved`, and so on) with no text. This has not been re-checked against live Gemini.

**Retry and idempotency.** One pending message is retried before retrieval and one more after each successful reply. Consent is rechecked before the provider call and again, with a row lock, before saving; deletion tombstones are checked at save time. A completion marker per message ID makes re-processing a no-op. Messages from before the latest opt-in are never back-filled.

**Check-ins.** A memory is eligible only when it is an active, non-sensitive `open_threads` or `life_events` row with a grounded `follow_up_question`, its `follow_up_after` time has passed (7 days after it was learned unless an event date says otherwise), it was mentioned within 45 days, it has never been checked on (`last_followed_up_at` is null), it is unresolved, and no check-in happened for this user in the last 7 days (the cooldown spans all chats). Only a plain greeting is an opening; a direct question never triggers one. The backend gives the model a single stored question and tells it not to claim an outcome. Resolution requires the user's own words (an exact quote validated against their message plus an explicit-resolution pattern). The chat route reads time from `main._now()` so tests control the clock.

**Context sent to the model.** Account chat: the current conversation, at most five relevant saved facts, at most three past-chat excerpts, an optional check-in question, and the trusted profile display name if one exists. Quick Chat: the single message only.
